## 3. BD-DEC-001 ユーザー識別

### 3.1 状態

確定設計。`UQ-001`を解決する基本方針としてユーザー承認済み。

### 3.2 関連する要件ID

- サービス前提: `BR-004`、`BR-005`、`BR-006`、`BR-022`、`BR-023`
- プレイヤー検索・識別: `FR-001`、`FR-002`、`DR-001`、`DR-002`
- 改善目標: `FR-040`〜`FR-052`、`DR-008`〜`DR-010`、`DR-016`、`DR-018`
- 試合レビュー: `FR-070`〜`FR-081`、`DR-011`〜`DR-015`
- セキュリティ・整合性: `NFR-013`、`NFR-020`、`NFR-023`
- 保守性: `NFR-030`〜`NFR-032`
- 完成条件: `AC-007`〜`AC-012`

### 3.3 採用した基本方針

- v1.0はログイン機能なしの個人利用とする。
- 内部的にアプリ利用者を表す所有者IDを持つ。
- アプリ利用者と、Riot APIでPUUIDにより識別するLoLプレイヤーを別の概念として扱う。
- 自分のメインLoLアカウントを1つ扱う。
- 他人のLoLアカウントも検索し、戦績と統計を閲覧できる。
- 改善目標、目標履歴、見直し記録、試合レビューは、自分のメインLoLアカウントに対してだけ作成、編集、削除できる。
- 他人のアカウントを検索しても、書き込み対象となるメインアカウントは切り替えない。
- 書き込み可否はUI表示だけに依存せず、サーバー側でも対象がメインアカウントであることを確認する設計とする。
- 将来の一般公開時には、認証とアクセス制御を別途設計する。

### 3.4 採用理由

- `BR-004`および`BR-022`の個人利用というv1.0の範囲を守り、認証機能を先行実装しないため。
- アプリ利用者と検索対象プレイヤーを分離し、他人のアカウントを閲覧した際の誤書き込みを防ぐため。
- 目標やレビューに所有者の概念を持たせ、将来の一般公開で既存データへ所有関係を追加する大規模な移行を避けやすくするため。
- UIの制御を回避したリクエストに対しても、サーバー側で書き込み範囲を守れる設計上の境界を設けるため。

### 3.5 将来拡張への影響

- 一般公開時には、内部所有者と認証アカウントを関連付ける設計が必要になる。
- 複数ユーザー化では、利用者ごとのデータ分離とアクセス制御を追加する必要がある。
- 一人の利用者が複数のLoLアカウントを所有する機能はv1.0の対象外とし、必要になった時点で関連付けを再設計する。
- Riot Sign Onなどの認証方式は本決定に含めず、将来の要件と利用条件を確認して決定する。

### 3.6 残る未決定事項

- 自分のメインLoLアカウントの初期登録方法
- メインPUUIDの変更方法と、変更時の既存目標・レビューの扱い
- 内部所有者IDの具体的なデータ構造、生成方法および初期データ作成方法
- サーバー側でメインアカウントへの書き込みを確認する具体的な処理境界
- 将来の認証方式とアクセス制御方式

これらは本書の後続検討または詳細設計で決める。現時点ではテーブル名、カラム、API、画面操作を確定しない。

## 4. BD-DEC-002 対象リージョン

### 4.1 状態

確定設計。`UQ-002`を解決する基本方針としてユーザー承認済み。

### 4.2 関連する要件ID

- 対象範囲: `SCP-001`〜`SCP-005`
- プレイヤー検索・エラー処理: `FR-001`〜`FR-006`
- 試合取得・保存: `FR-010`〜`FR-017`
- 戦績表示: `FR-020`〜`FR-028`
- データ: `DR-001`〜`DR-007`
- 外部APIの信頼性: `NFR-001`〜`NFR-005`
- データ整合性: `NFR-020`〜`NFR-022`
- テスト: `NFR-040`〜`NFR-042`
- 完成条件: `AC-001`〜`AC-006`、`AC-015`、`AC-016`

### 4.3 採用した基本方針

- v1.0の正式対応プラットフォームはJP1とする。
- ACCOUNT-V1およびMATCH-V5のリージョナルルーティングにはASIAを使用する。
- プラットフォームとリージョナルルートを別の設定値として管理する。
- Riot APIの接続先は設定へ集約し、コードの各所へ直接埋め込まない。
- v1.0ではリージョン選択UIを設けず、日本サーバーだけに対応することを画面上で示す。
- 将来の複数リージョン対応を考慮した境界を設けるが、複数リージョン機能自体はv1.0で実装しない。
- Riot IDのタグラインだけで所属サーバーを判断しない。
- 所属サーバーを確認できない場合、海外サーバー所属と断定しない。

### 4.4 採用理由

- `BR-004`および`BR-022`の個人利用・実利用検証に必要な範囲へv1.0を限定するため。
- 複数リージョン対応による入力、ルーティング、エラー処理、データ管理、テストの増加をv1.0へ持ち込まないため。
- プラットフォームとリージョナルルートを分離し、将来の対応地域追加でAPI接続処理全体を作り直すことを避けるため。
- タグラインから所属を推測せず、確認できない状態を誤って未対応や対象試合なしとして扱わないため。

### 4.5 将来拡張への影響

- 将来の複数リージョン対応では、対応プラットフォームとリージョナルルートの組み合わせを追加する。
- リージョン選択または所属の自動確認を導入する場合は、UI、API処理、保存データ、エラー表示およびテストを追加する。
- API接続先を設定へ集約するため、地域追加時の変更箇所を限定しやすくする。
- 複数リージョン機能の実装時期と対象地域は、本決定では確定しない。

### 4.6 残る未決定事項

- Riot APIを使用したJP1所属の具体的な確認方法と確認タイミング
- 所属不明、未対応リージョン、対象試合なしを区別する内部状態とユーザー向けエラー処理
- 将来のルーティング設定の形式と管理場所
- プラットフォームおよびリージョナルルートを保持する具体的なデータ構造
- 将来の複数リージョン対応で、リージョン選択と自動確認のどちらを採用するか

これらは本書の後続検討または詳細設計で決める。現時点では設定ファイルの形式、DBカラム、API呼び出し手順を確定しない。

## 5. BD-DEC-003 システム構成・責務分担

### 5.1 状態

確定設計。v1.0のシステム構成として、段階的に構築するモジュラーモノリスを採用することがユーザー承認済み。

### 5.2 関連する要件ID

- 既存資産の継承: `BR-006`
- プレイヤー検索・外部APIエラー: `FR-001`〜`FR-006`
- 試合取得・保存: `FR-010`〜`FR-017`
- 改善目標・レビュー: `FR-040`〜`FR-081`
- データ整合性: `DR-001`〜`DR-018`、`NFR-020`〜`NFR-023`
- 外部API・セキュリティ: `NFR-001`〜`NFR-015`
- 保守性・拡張性: `NFR-030`〜`NFR-032`
- テスト: `NFR-040`〜`NFR-042`
- 完成条件: `AC-006`、`AC-015`〜`AC-017`

### 5.3 採用したシステム構成

- v1.0は、単一のFlaskアプリケーションと単一のMySQLデータベースで構成するモジュラーモノリスとする。
- マイクロサービスへの分割、Redis、バックグラウンドジョブは、v1.0のシステム構成の前提にしない。
- FlaskのApplication Factoryでアプリ生成、設定読込、共通初期化、Blueprintおよびエラーハンドラの登録を行う構成とする。
- FlaskのルーティングはBlueprintで機能単位に分割し、HTTP入力、基本的な入力検証、サービス呼び出し、HTTPレスポンスへの変換を担当する。
- サービス層は、プレイヤー検索、試合取得、目標、レビューなどのユースケース進行と業務ルールを担当する。
- Riot API通信は専用クライアントへ分離し、URL構築、認証ヘッダー、タイムアウト、HTTPステータス、JSON応答の処理を担当する。
- DBアクセスはリポジトリへ分離し、MySQLへの取得、追加、更新とDB固有エラーの変換を担当する。
- 設定管理は、秘密情報、JP1とASIAのルーティング、タイムアウトなどをコードの各所へ分散させない責務を持つ。
- メインアカウントへの書き込み可否はサービス層または独立したポリシーで判定し、クライアントから送られたPUUIDや所有者IDを権限判定の根拠としてそのまま信用しない。
- 共通エラー処理は、内部例外を秘密情報や外部APIの内部応答を含まない安全なHTTPレスポンスへ変換する。
- `app.py`は既存の起動方法を引き継ぐ薄い入口とし、既存の `templates/` と `static/` は段階移行中も当面現在の配置を維持する。

### 5.4 段階的な構築方針

1. 現行の画面と検索処理を維持したまま、Application Factoryと最初のBlueprintを導入する。
2. 現行の `requests` によるRiot API通信を専用クライアントへ移す。
3. プレイヤー検索と試合取得の処理順序・業務ルールをサービス層へ移す。
4. MySQL導入時にDB接続とリポジトリを追加する。
5. 改善目標とレビューの実装時に、メインアカウントだけへ書き込めるポリシーを追加する。
6. 各段階で既存動作と関連要件を確認し、一括した大規模な作り直しを避ける。

この順序は構成上の移行方針を示す。個別機能の詳細設計、実装順およびコミット単位は別途決定する。

### 5.5 採用理由

- 現行のFlaskアプリを活かしながら、小さな単位で責務を分離できるため。
- `NFR-030`が求めるルーティング、Riot API通信、データ変換、DBアクセス、設定の分離を実現しやすいため。
- `NFR-031`および`BR-006`に従い、大規模な一括作り直しを避けられるため。
- Riot API通信を専用クライアントに分けることで、`NFR-040`と`NFR-041`が求めるモックテストを作りやすくなるため。
- 目標・レビューの書き込み制約をサービス層へ集約し、UIだけに依存しない確認を実現しやすいため。
- 案Aの最小分割より拡張性が高く、完全なクリーンアーキテクチャより学習・実装コストを抑えられるため。
- 一つのアプリとして実行・デバッグでき、Flask、Python、HTTP、DBの役割を段階的に学習しやすいため。

### 5.6 構成要素の責務

| 構成要素 | 主な責務 | 担当しないこと |
|---|---|---|
| `app.py` | アプリ生成・起動の入口 | API通信、業務ルール、SQL |
| Application Factory | 設定読込、共通初期化、Blueprint・エラーハンドラ登録 | 個別ユースケース |
| Routes / Blueprints | HTTP入力、基本検証、サービス呼び出し、HTTPレスポンス変換 | Riot API直接通信、SQL、書き込み可否の最終判断 |
| Services | ユースケース進行、業務ルール、対象queue制限、書き込み可否の確認 | Flaskの `request`、具体的なHTTP通信、具体的なSQL |
| Riot API Client | Riot APIへのHTTP通信、タイムアウト、ステータス・応答処理 | DB更新、画面文言、所有者判定 |
| Repositories | MySQLへのデータアクセス、DB固有エラーの変換 | Riot API通信、HTTPレスポンス生成 |
| Domain Policy / Calculations | メインアカウント書き込み判定、KDAなどの純粋な規則・計算 | HTTP通信、DB接続、画面表示 |
| Config | 秘密情報、JP1・ASIA、環境別設定の集約 | ユースケース判断、秘密情報の外部出力 |
| Error Handler | 内部例外から安全なHTTPレスポンスへの変換 | 原因の握りつぶし、秘密情報の表示 |

### 5.7 将来拡張への影響

- 機能単位のBlueprintとサービスを追加することで、目標、レビュー、統計を単一アプリ内で段階的に拡張できる。
- 将来認証を導入する場合も、既存のサービスと書き込みポリシーへ認証済み所有者の確認を追加しやすい。
- 将来の複数リージョン対応では、設定とRiot APIクライアントを中心に変更範囲を限定しやすい。
- モジュール間の依存を保つため、ルートからリポジトリを直接呼ぶ、リポジトリからRiot APIを呼ぶなどの責務逆流を避ける。
- 将来さらに規模が拡大した場合も、必要性を確認してから一部モジュールの独立を検討できる。v1.0では独立サービス化しない。

### 5.8 残る未決定事項

- 他人の戦績データをMySQLへ保存する範囲、保存目的、保存期間およびキャッシュとの区別
- 内部所有者IDの具体的なデータ構造、初期作成方法および取得方法
- メインPUUIDの初期登録、保存、参照、変更方法と、変更時の既存データの扱い
- Riot API通信の前後でDBトランザクションをどこから開始し、どこで終了するかという具体的な境界
- Riot API取得成功後にDB保存が失敗した場合、およびDB更新途中で失敗した場合の回復方法
- Blueprintの最終的な分割数、URLおよびファイル名
- MySQLドライバ、ORM、マイグレーション手段（`UQ-019`）
- キャッシュの保存先、TTL、再取得条件（`UQ-028`）
- 接続・応答タイムアウト値、429時の再試行方針
- 具体的な例外クラス、APIレスポンス形式、ログ項目
- テストツール、カバレッジ目標およびCI導入時期（`UQ-032`）

これらは後続の基本設計または詳細設計で決める。特に、他人の戦績の保存範囲、所有者ID・メインPUUIDの管理、Riot API通信とDBトランザクションの具体的な境界は、本決定では確定しない。
